### 🏗️ Общая архитектура
Приложение построено по принципам событийно-ориентированной микросервисной архитектуры (Event-Driven Architecture) с использованием паттернов Outbox и Inbox для гарантированной доставки сообщений.

### 🚪 1. API Gateway (`gateway:8081`)
Центральная точка входа, обеспечивающая безопасность, стабильность и маршрутизацию.

* **Безопасность и валидация**:
   * Проверка JWT-токена с использованием публичных ключей Keycloak.
   * Инъекция заголовков для downstream-сервисов (извлекаются из токена): `X-User-Id`, `X-User-Name`, `X-User-Email`. Это избавляет нижележащие сервисы от необходимости парсить JWT.
* **Ограничение нагрузки (Rate Limiting)**:
   * Реализовано через **Redis**.
   * Два уровня лимитирования: по IP-адресу клиента и по идентификатору пользователя (User ID).
* **Маршрутизация и отказоустойчивость**:
   * Роутинг запросов в `draw-core:8082` или `notify-worker:8083`.
   * **Fallback-контроллеры**: При недоступности целевых сервисов запросы перенаправляются локально через `forward:/fallback/draw-core` или `forward:/fallback/notify-worker` для возврата корректных ответов об ошибке (Graceful Degradation).

### ⚙️ 2. Draw Core (`draw-core:8082`)
Ядро бизнес-логики: управление жизненным циклом розыгрышей и билетами.

#### 📊 Модель состояний розыгрыша (State Machine)
* `CREATED`: Создан, но ещё не активирован.
* `ACTIVATED`: Активирован, идёт приём билетов.
* `COMPLETED`: Завершён, победитель определён.
* `CANCELLED`: Отменён.

#### 🛠️ REST API Endpoints
* `POST /api/draws` → Создание розыгрыша (статус `CREATED`).
* `GET /api/draws/{id}` → Получение детальной информации о розыгрыше.
* `POST /api/draws/{id}/activate` → Перевод `CREATED` → `ACTIVATED`.
* `POST /api/draws/{id}/complete` → Проведение розыгрыша (`ACTIVATED` → `COMPLETED`).
* `POST /api/draws/{id}/cancell` → Отмена (`CREATED` или `ACTIVATED` → `CANCELLED`).
* `POST /api/tickets` → Покупка билета (строго валидирует, что статус розыгрыша `ACTIVATED`).
* `GET /api/tickets/draw/{drawId}` → Получение списка всех купленных билетов.

#### 🔄 Workflow завершения розыгрыша (`complete`)
1. **Внешний вызов**: Обращение к API `randomOrg` для получения криптографически стойкого случайного индекса из списка билетов (`List<Ticket>`).
2. **Локальная транзакция (ACID)**: В рамках одной транзакции PostgreSQL выполняются два действия:
   * Изменение статуса розыгрыша на `COMPLETED`.
   * Сохранение записи в таблицу `outbox_event` со статусом `published = false`.
   * *Гарантия*: Атомарность гарантирует, что событие будет отправлено тогда и только тогда, когда состояние в БД успешно изменено.

#### ⏱️ Outbox Poller
* **Механизм**: Запланированная задача (`@Scheduled`), выполняющаяся каждые **5 секунд**.
* **Логика**: Выполняет запрос `findByPublishedFalse`. Для каждой найденной записи отправляет сообщение в Kafka-топик `draw-events`.
* **Финализация**: При успешном получении acknowledgment от Kafka, статус записи обновляется на `published = true`.

#### 🗄️ Хранилище
* **PostgreSQL** (`db:draw-core`): Хранит сущности `Draw`, `Ticket` и таблицу `outbox_event`.

### 📨 3. Apache Kafka (`draw-events`)
Шина событий для асинхронной коммуникации между `draw-core` и `notify-worker`.

* **Топик**: `draw-events`
* **Ключ (Key)**: `String` (строковое представление UUID агрегата, например, `drawId`). Обеспечивает порядок сообщений для одного розыгрыша (partitioning by key).
* **Значение (Value)**: `JSON`.
* **Сериализация (Producer)**:
   * Key Serializer: `ToStringSerializer`
   * Value Serializer: `JsonSerializer`
* **Полиморфная десериализация (Jackson)**:
   * В корень JSON автоматически добавляется дискриминатор `"type"` (например, `"DrawCompleted"`). Это позволяет потребителю корректно маппить JSON на конкретный Java-класс события.
* **Пример Payload (`DrawCompleted`)**:
  ```json
  {
    "type": "DrawCompleted",
    "drawId": "123e4567-e89b-12d3-a456-426614174000",
    "winnerEmail": "winner@example.com",
    "winnerName": "Иван Иванов",
    "drawName": "Новогодний розыгрыш"
  }
  ```

### 📬 4. Notify Worker (`notify-worker:8083`)
Сервис обработки событий и отправки уведомлений, реализующий паттерн **Transactional Inbox**.

#### 🔄 Workflow обработки событий (Idempotency & Reliability)
1. **Kafka Listener**: При получении сообщения из `draw-events`:
   * **Сначала** сохраняет событие в локальную БД в таблицу `inbox_event` со статусом `published = false`.
   * **Только после успешного сохранения** отправляет acknowledgment (ack) в Kafka.
   * *Гарантия*: Исключает потерю сообщений при падении сервиса до обработки и обеспечивает идемпотентность (повторное получение того же сообщения не сломает логику, так как оно уже будет в БД).
2. **Inbox Event Poller**:
   * Периодически выполняет `findByPublishedFalse`.
   * Вызывает `emailService.send()` для каждого события.
   * При успешной отправке обновляет статус на `published = true`.

#### 🛡️ Email Service & Resilience
* Интеграция с **Mailhog** (тестовый SMTP-сервер).
* **Механизм устойчивости (Resilience)**: До **3 попыток** повторной отправки (retry) при временных сбоях сети или недоступности Mailhog.

#### 🛠️ REST API Endpoints (для ручного управления и мониторинга)
* `GET /api/inbox/unpublished` → Возвращает все "зависшие" или ещё не обработанные inbox-события (`published = false`). Полезно для мониторинга и отладки.
* `POST /api/inbox/resend` → Ручной триггер для принудительного запуска `inboxEventPoller` (например, после исправления проблемы с Mailhog).

#### 🗄️ Хранилище
* **PostgreSQL** (`db:notify-worker`): Хранит только таблицу `inbox_event`.

### 🌐 End-to-End Workflow: Завершение розыгрыша
1. Клиент отправляет `POST /api/draws/{id}/complete` → **Gateway**.
2. **Gateway** проверяет JWT, лимиты (Redis), добавляет заголовки `X-User-*` и маршрутизирует запрос в **Draw-Core**.
3. **Draw-Core** запрашивает случайный индекс у **RandomOrg**.
4. **Draw-Core** открывает транзакцию PostgreSQL: обновляет статус розыгрыша на `COMPLETED` и вставляет запись в `outbox_event` (`published=false`). Коммит.
5. **Outbox Poller** (через ≤5 сек) вычитывает новую запись и публикует JSON-сообщение в Kafka-топик `draw-events`.
6. **Notify-Worker (Kafka Listener)** получает сообщение, сохраняет его в `inbox_event` (`published=false`) и делает ack в Kafka.
7. **Inbox Poller** вычитывает неподтверждённое событие и вызывает `emailService.send()`.
8. **Email Service** отправляет письмо победителю через **Mailhog** (с до 3 retry при ошибках).
9. При успехе **Inbox Poller** обновляет статус записи на `published=true`.

### 💡 Ключевые архитектурные паттерны и гарантии
* **Двойная запись (Outbox/Inbox)**: Гарантирует *At-Least-Once* доставку без распределённых транзакций (2PC).
* **Идемпотентность**: Достигается за счёт сохранения события в Inbox до ack и уникальности ключа сообщения в Kafka.
* **Graceful Degradation**: Fallback-маршруты в Gateway предотвращают каскадные сбои и возвращают понятные ответы клиенту.
* **Безопасность**: Централизованная валидация токенов и rate limiting на границе системы защищают внутренние сервисы от перегрузки и несанкционированного доступа.
